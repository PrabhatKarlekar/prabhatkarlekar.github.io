## 2. Performance: the biggest architectural opportunity

Your website is built using plain HTML, CSS, and JavaScript. For this type of portfolio, I consider that a good starting point. You do not need to migrate to React, Next.js, or another framework simply to make the website feel modern.

The opportunity is to make the existing implementation leaner.

### A. Remove or redesign the neural background

Your `script.js` contains a canvas animation with up to 40 particles on mobile and 70 on desktop. It redraws the canvas on every animation frame and calculates the distance between every pair of particles.

With 70 particles, that means 2,415 unique particle-pair checks per frame before accounting for drawing operations. At 60 frames per second, that is approximately 144,900 pair checks per second.

That calculation is not a benchmark of actual CPU usage, but it explains why the effect has a nonzero and continuous computational cost.

My recommendation:

- Prefer a static, subtle background as the default.
- If you retain the animation, pause it when the page is hidden.
- Avoid restarting the animation on every resize event without a debounce or appropriate scheduling.
- Keep the existing reduced-motion support.
- Test battery consumption and responsiveness on lower-powered mobile devices.
- Ensure the animation never competes with text or interactive elements.

I would not remove all visual character. I would simply ensure that the website's visual identity does not require continuous computation.

### B. Reduce external dependencies

Your HTML loads two external font families from Google Fonts and Font Awesome 6.4.0 from a CDN. It also loads a remote GitHub statistics image from a Vercel-hosted service.

Each dependency can introduce network requests, latency, availability concerns, and some additional privacy exposure.

## Dependency review

Google Fonts

Inter and JetBrains Mono are a reasonable pairing, but I would check which weights are actually used. Keep only the necessary weights or consider self-hosting optimized font files.

Font Awesome

The site uses many icons. Keep a consistent icon style, but evaluate whether loading the complete icon stylesheet is worth the cost. A small set of inline SVG icons may be sufficient.

Remote GitHub statistics

Treat this as optional content. If it loads slowly or fails, the rest of the portfolio should remain unaffected. A static contribution summary or a simple GitHub profile link may be a better trade-off.

I would not automatically remove every external dependency. I would measure each one, decide whether it contributes meaningful value, and keep the smallest set that meets your requirements.

### C. Simplify the JavaScript lifecycle

Your script currently has several overlapping mechanisms:

- `initNavigation()` installs a scroll listener.
- A separate global scroll handler repeats active-navigation calculations.
- `initAnimations()` observes project cards, timeline items, and skill categories.
- `initScrollAnimations()` installs another observer for sections and additional observers for metrics.
- The page-visibility handler calls `init()`, which returns early because the application is already initialized.

This is more complicated than a portfolio needs.

I would consolidate the behavior into a small number of well-defined modules:

1. Theme preference and toggle.
2. Mobile navigation.
3. Active-section tracking.
4. Optional entrance animations.
5. Metric presentation, if retained.
6. Contact handling, only if a real submission mechanism exists.

The goal is not to minimize the number of lines at all costs. It is to reduce unnecessary event listeners, duplicated calculations, and code paths that are difficult to reason about.

### D. Improve animation behavior

Your typewriter effect reveals three professional descriptors sequentially. That can be visually appealing, but it introduces a delay before all the role information is displayed.

I would either display the descriptors as static text or use a subtle animation that does not hide essential information from users or assistive technology.

The project cards and sections also animate into view. I would retain only effects that make navigation feel smoother, and I would ensure that reduced-motion preferences disable nonessential movement consistently across the site.

### E. What we cannot conclude yet

I have not measured the site's actual bundle size, time to first render, LCP, INP, CLS, or memory usage. The source indicates where optimization opportunities exist, but only browser testing can establish whether those opportunities translate into measurable improvements.

### Phase 4 — Design system and visual refinement

I agree with consolidating the color palette, removing arbitrary skill percentages, and improving contrast. But I would adjust three recommendations.

First, verify the seven contrast failures before fixing them. The ratios in your plan are useful leads, not a substitute for checking the exact foreground/background pairs in the final design. Contrast can change depending on opacity, gradient position, theme, and text size. WCAG AA generally requires 4.5:1 for normal text, 3:1 for large text, and 3:1 for visual information in relevant interface components.

For the focus ring, use a clearly visible outline with sufficient contrast against adjacent colors. Do not simply make every focus ring solid white or blue; the appropriate color depends on the surrounding surface.

Second, replace hardcoded colors without overengineering CSS. Centralize the primary palette and reusable design tokens, but do not turn every one-off decorative color into a complicated variable system. The aim is consistency and maintainability.

Third, preserve your visual identity. A restrained blue accent, a distinctive typography pairing, and subtle technical diagrams could work very well. You do not need to eliminate every gradient or rounded card to avoid looking like a template. The problem is repetition without purpose, not gradients themselves.

I would also add a typography and spacing audit that checks long project titles, code labels, text wrapping, and the mobile layout.

#### A correction to the canvas cost estimate

The figure of approximately 144,900 pair checks per second assumes 70 particles, 60 frames per second, and all unique pairs being evaluated on every frame. That is a useful theoretical estimate, but it does not prove that the animation is a significant bottleneck on the devices visitors actually use.

I would keep the canvas optimization high on the list because it runs continuously and is decorative. I would not claim a specific CPU or battery improvement until the optimized version is tested.

#### Add explicit performance budgets

This is missing from your plan. Set practical targets for the deployed site, then check them after each major change.

I would track:

- Compressed initial HTML, CSS, JavaScript, font, and image payloads.
- Total initial network requests and third-party requests.
- LCP, INP, and CLS.
- Lighthouse performance and accessibility results.
- The behavior of the page on a slower mobile connection.

For Core Web Vitals, use the standard good thresholds of LCP ≤ 2.5 seconds, INP ≤ 200 milliseconds, and CLS ≤ 0.1 at the 75th percentile when real-user data is available.

Do not optimize only for a Lighthouse score. A good score is helpful, but the actual experience and content quality matter too.

### Phase 6 — SEO, security, accessibility, and polish

This phase is good, but it combines several distinct disciplines. I would keep the overall phase and treat the following as separate checklists.

#### SEO: what I would keep and what I would add

I agree with adding a proper favicon, Open Graph metadata, canonical URL, social card metadata, `robots.txt`, a sitemap, and a 404 page where useful.

I would make JSON-LD optional rather than a blocking task. A simple `Person` schema can be useful if it accurately describes you and points to real profiles, but it will not automatically improve rankings.

Also, `robots.txt` and `sitemap.xml` should be validated rather than added mechanically. A sitemap is useful for discovery, but it is not a substitute for crawlable page content and correct metadata.

One important repository correction: if you want a proper GitHub repository landing page, create or update the root-level `README.md`. A `.github/README.md` file does not serve the same purpose as the repository's main README. The `.github` directory is appropriate for contribution templates, issue templates, and certain community-health files.

#### Security: three details I would change

1\. Do not rely on a meta CSP as a complete security-header solution.

GitHub Pages has limitations on configuring arbitrary HTTP response headers. A Content Security Policy delivered through a meta element can provide some protections, but it does not support every directive available in an HTTP header and can break legitimate resources if configured too aggressively.

Before adding a CSP, inventory the actual scripts, styles, fonts, and images. Test the policy carefully, and use hosting-level header configuration if you later move to a platform that supports it.

2\. Pin GitHub Actions to full commit SHAs.

This is a sensible supply-chain security improvement. Use verified commit SHAs for third-party actions, review updates deliberately, and retain the workflow's least-privilege permissions.

Concurrency control is also useful to avoid overlapping deployments, but it is a reliability measure rather than a substitute for pinning actions or limiting permissions.

3\. Apply `rel="noopener noreferrer"` selectively.

Use `noopener` for links opening new tabs when appropriate; modern browsers already provide implicit `noopener` behavior for many `target="_blank"` links. Add `noreferrer` when you also intend to suppress referrer information. It is a privacy choice, not a requirement for every ordinary external link.

#### Accessibility: additions I would make

Your plan already covers skip links, labels, focus indicators, icon accessibility, theme state, and reduced motion. I would add:

- Verify the accessible name and state of the mobile menu and theme toggle.
- Test screen-reader announcements for form validation and submission.
- Ensure animated numbers have sensible accessible text.
- Confirm the content order remains logical when CSS layout changes.
- Test the page at 200% zoom and on narrow viewports.
- Validate contrast in every supported theme.
- Test that content remains visible when JavaScript fails.
- Check the résumé PDF for selectable text, reading order, and basic accessibility.

Not all 44 icons should automatically receive `aria-hidden="true"`. Decorative icons should be hidden from assistive technology; meaningful icons need an accessible name or accompanying text, and interactive icons must be part of correctly labeled controls.

#### Privacy: I support the proposed cleanup

Removing the phone number and using a less precise location is a sensible default for a public portfolio. I would keep a dedicated professional contact route and ensure the location is accurate if you choose to display it.

For identity consistency, choose the name used in your résumé and professional profiles as the main display name. You do not need to force your GitHub username or email address to match your display name, as long as the identity is clear and the links lead to the correct person.

#### Repository hygiene: one important caveat

Delete obsolete résumé files from the current published directory once the new file is verified and all links have been updated. But remember that deleting a file in a new commit does not necessarily remove earlier copies from Git history. If a file ever contained sensitive information, the appropriate response is different from ordinary cleanup.
